# Public Face Workstreams

**Date:** 2026-05-07
**Purpose:** turn the 2026-05-07 public-face research into an ordered action
backlog

## P0 - Canonical Story Alignment

**Outcome:** root domain, staging page, README, and GitHub all describe the
same product in the same category.

### Tasks

- choose one canonical one-liner for iHomeNerd
- make `ihomenerd.com` the clearest public homepage, not just a pointer to
  staging
- align root hero, staging hero, README opener, and repo description
- move install-path caveats below product value and primary use cases
- decide whether staging remains public preview, internal preview, or a domain
  alias

### Done means

- an outsider can explain iHomeNerd correctly after 15 seconds on the root page
- root and staging no longer read like different products

## P0 - Public Standing Review Protocol

**Outcome:** public-face improvements can be measured with repeatable evidence
instead of vibes.

### Tasks

- define stable public panel prompts
- create a 1-5 scorecard for public understanding and trust
- track wrong outsider inferences as public-face bugs
- create dated before/after review folders
- run the baseline before or alongside root/staging story alignment

### Done means

- every public-face sprint can say what improved, what stayed confusing, and
  which wrong inferences were resolved

## P0 - Trust, Openness, and Repo Hygiene

**Outcome:** the public repo stops creating avoidable trust friction.

### Tasks

- decide and publish a top-level license
- decide exact public wording for `open source`, `open core`, or
  `public repo / paid layers`
- add GitHub repo description, homepage, and topics
- add a `START_HERE` or stronger onboarding section for cold visitors
- add at least one screenshot or short demo asset

### Done means

- outsiders do not have to guess whether reuse is allowed
- GitHub itself explains the repo before the visitor opens code folders

## P1 - Search and AI Discoverability

**Outcome:** search engines and AI summarizers receive cleaner canonical
signals.

### Tasks

- add `robots.txt`
- add `sitemap.xml`
- make canonical/OG URLs point to the intended public domain
- tighten page titles and descriptions around the actual product story
- create/share a social preview image that matches the current product message

### Done means

- root domain becomes the primary crawl target
- staging-specific wording no longer dominates metadata

## P1 - Public Evidence Pack

**Outcome:** the project is easier to trust because the public surface shows
what exists today.

### Tasks

- capture screenshots of the landing page and Command Center
- create one architecture diagram for root page / README reuse
- create a simple `What works today / What is preview / What is planned` table
- document supported install paths honestly

### Done means

- the site and repo can show product reality, not just describe it

## P2 - Launch Posture and Review Rhythm

**Outcome:** the public face evolves intentionally instead of drifting between
surfaces.

### Tasks

- define a recurring public-face review checklist
- require dated claims for readiness and install guidance
- keep one backlog of public claims that changed and need propagation
- use this lane for future audits after major landing or repo changes

### Done means

- public-face upkeep becomes routine product work rather than cleanup after the
  fact
