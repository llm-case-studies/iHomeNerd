# Participant Invite: Client Surface Boundary Review

Use or adapt this note when inviting AI or human contributors into the
discussion sprint.

---

Please review the discussion sprint at:

- `docs/expert-briefs/initiatives/uniform-web-ui/active/2026-05-04_client-surface-boundary-review/`

Start with:

1. `README.md`
2. `01-seed.md`
3. `04-portfolio-working-list.md`

Then respond using:

- `02-feedback-template.md`

Scope:

- no coding
- no testing
- no implementation branch changes

Focus on:

- what belongs in stable core iHN surface
- what belongs in adapter/plugin/helper space
- what should remain app-owned workflow or UX
- which products are true clients versus sibling products or deployment variants

Important:

- treat the current structure as a strong draft, not a final doctrine
- challenge the assumptions when needed
- prefer concrete route/capability examples over abstract commentary
- do not assume that every useful helper should become a stable public route

Strong contribution patterns:

- reclassify one or more products in the portfolio
- identify one helper/capability that should move out of core
- identify one primitive that should stay or become core because multiple apps need it
- call out one unresolved tension that should survive into synthesis

Desired outcome:

- sharper conceptual boundaries
- a smaller number of real follow-on coding/testing sprints
- less route leakage from app-specific semantics into iHN core
