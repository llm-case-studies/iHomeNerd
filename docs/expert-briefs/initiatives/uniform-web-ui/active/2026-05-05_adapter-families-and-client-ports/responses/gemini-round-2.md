# Round 2 Response: Adapter Families and Client Ports

## Reviewer

- **Name / model:** Gemini 3.1 Pro (High)

---

### Tension 1: Is Monitoring/triage a real adapter family?

**Position:** Yes, it is a real (though narrow) adapter family, but strictly as an installable plugin.
**Why:** Initially, I viewed this as too domain-specific. However, reading Grok and DeepSeek's arguments persuaded me. The structural pattern (watch → detect → prioritize → route) is an event loop that should run on the node, not the client. If we force clients like On-My-Watch or Edge-Kite to poll the node's vision and chat APIs, we waste bandwidth and battery. A thin, server-side monitoring family that handles event subscriptions and triggers is justified, provided domain-specific alert UX stays app-owned.

### Tension 2: Should Planning/recommendation be dropped as a family?

**Position:** Agree — drop it.
**Why:** A "plan" is just a structured output generated by chat and evaluated by domain rules. Tax planning, lesson progression, and scam mitigation share no reusable server-side structure beyond the core `/v1/chat` and `/v1/rules` engines. Attempting to generalize planning on the server will result in a hollow, useless abstraction. It is fundamentally a client-side composition pattern.

### Tension 3: Should Data/external connectors be the 7th family?

**Position:** Yes, it is a real server-side family (Plugin space).
**Why:** DeepSeek's proposal aligns perfectly with my stance on Tension 4. If iHN is the central privacy boundary and proxy (Model A), then iHN *must* be the entity connecting to external threat feeds or legal databases. If the node lacks a data connectors family, clients will be forced to build their own bridges, bypassing the node entirely and breaking the local-first trust model.

### Tension 4: Provider adapters — iHN-only or multi-provider client?

**Position:** Model A (iHN-only) must be the primary architecture.
**Why:** I strongly maintain my Round 1 position. Allowing client apps to directly connect to OpenAI or Azure completely shatters the privacy and auditability promises of the iHN platform. The node must handle backend switching and cloud fallbacks, governed by household-level user consent. DeepSeek's suggestion to sequence them (Model A first, Model B later) is pragmatic for port design, but Model B should remain an anti-pattern for first-party clients.

### Tension 5: Should "1 family = 1 plugin_id" be the mapping rule?

**Position:** Accept.
**Why:** GLM's mapping proposal is elegant and strictly enforces the boundary model. Tying the URL structure directly to the adapter family (`/v1/plugins/{family_id}/...`) turns a conceptual taxonomy into a machine-checkable architecture constraint. If a proposed helper cannot fit under an existing family namespace, it forces a deliberate architectural review before merging.

### Tension 6: When should client-mirror discussions start?

**Position:** Sequential (wait for stabilization).
**Why:** I have changed my position based on DeepSeek's insight. The implementation gap is real: no client currently uses capability ports. If we mirror the discussion into PronunCo now, the team will optimize the ports for their existing monolithic logic. We need a working reference first. We should prototype the capability port layer in the Command Center (which already uses core primitives), stabilize the pattern, and *then* mirror the discussion to PronunCo and iLegalFlow.

### Tension 7: Is policy/orchestration a separate layer or part of app core?

**Position:** Separate layer.
**Why:** GLM argues that separating it creates "weird indirection" on mobile. While true that Hexagonal Architecture can feel verbose, collapsing policy into the App Core violates the separation of concerns. The App Core should contain purely deterministic business logic (making it highly unit-testable). Policy handles network retries, timeouts, offline fallbacks, and caching. Mixing volatile network logic with business logic makes the core brittle and hard to test. The indirection is the price of resilience.

### New insights from other reviewers
- **The Implementation Gap (DeepSeek):** The observation that we are separated from this architecture by 3-4 layers of missing infrastructure (no plugin registration, no capability ports) is sobering. It correctly calibrates how much refactoring is required before this becomes reality.
- **Contract Shape vs. Cognitive Work (Qwen):** Renaming families by their structural contract rather than their "brain demand" is a crucial insight. "Audio I/O" is a better family name than "Speech" because it describes what the adapter actually manages.
